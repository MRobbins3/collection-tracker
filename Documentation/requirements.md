# Collection Tracker — Requirements

Living document. Status values: `planned` · `in progress` · `shipped` · `deferred`.

Every PR that changes user-visible behavior updates this file in the same commit/PR.

## Vision

A single mobile-first web app where users track collections of *any* kind of thing — Lego sets, Funko Pops, coins, stamps, trading cards, plants, books, vinyl, whatever. Browsing categories is public; saving a collection requires a Google sign-in. Installable as a PWA; native-app wrap via Capacitor is a future option.

## Phase 2 — Catalog + community contributions

The long-term product is a **two-layer model** (ADR 0004): a pre-loaded global catalog per category plus user-owned item records that reference it. Captured here as a first-class roadmap so today's work doesn't preclude it.

- **Seeded catalog per category** — a starter list of known items, so users pick from it to add items without typing. **Sample shipped** (20 cited entries across Lego sets, vinyl records, and coins, in the dev seed set only); **the real dataset is pending the owner** and replaces the sample when it lands.
- **Browse the global catalog** — **shipped.** Each category page lists its approved catalog entries with search (name or identifier, e.g. set number) and "Show more"; each entry has a detail page. Signed-in users see "In your collection" markers and can add an entry to an existing or new collection (an item linked to the entry, details filled in).
- **User-submitted catalog entries** — **shipped.** "Can't find it? Suggest it for the catalog" in the add-item flow (or "Also suggest it for the catalog" when entering manually) and "Suggest this for the catalog" on a free-form item send a suggestion: name, category details (validated against the schema), optional description. The name and identifier are normalized and checked against approved *and* pending entries (ADR 0011): an approved match is reused (and the item linked to it), a pending one is reported, and only a new thing is queued (`status = pending`, `source = user_submitted`). Suggestions are private until approved; the item they came from is linked automatically on approval. Each user can have at most 20 requests waiting (ADR 0012).
- **Admin role + moderation queue** — **shipped.** `users.role` (null for almost everyone, `admin` for reviewers; assigned by an operator, never self-service, see ADR 0012). Admins get "Moderation" in the account menu: pending suggestions and corrections, oldest first, filterable by type and category, each with a detail page (a before/after diff for corrections) and Approve, Edit then approve, Reject (with a reason the submitter sees), or, for a duplicate suggestion, Merge into an existing entry. Decisions record who, when, the outcome, the reason, and the values before and after; approving sets `approved_by` / `approved_at`. Two admins can't both decide the same request.
- **Catalog supplements / corrections** — **shipped.** "Suggest a correction" on a catalog entry page proposes changed fields plus an optional note; nothing changes until an admin approves, and the audit trail keeps the previous values. Outcomes for suggestions and corrections show in "My submissions" (no email).
- **Catalog-backed autocomplete in the item-add UI** — **shipped.** Typing in "Add an item" searches the collection's category catalog; picking a match links the new item and fills in its name and details (still editable), and "enter manually" stays first-class.
- **User-built categories** — **shipped** (ADR 0013, Proposed). "Create a category" (on Categories and in the overview's "Add a category" panel) builds a category from fields approved categories already use (a searchable library grouped by category, de-duplicated by title and type), with your own options for text fields (normalized; typing an existing option in another case reuses it; Title Case suggested, deliberate casing kept), an optional "tells items apart" field, and a live preview of the item form. It's private and usable at once (collections, items, pins); people who may see your collections see it with them. "Submit for the public list" sends it to the admin queue; approval puts it in everyone's category list, rejection keeps it private with the reviewer's reason. Brand-new custom fields (not from the library) and changes after approval are not built yet (see the review file).
- **Backfill for MVP-era items** — **shipped.** "Find in catalog" on a free-form item suggests likely matches (same name and/or identifier, or a similar name) and links only the one the owner picks; linked items can be unlinked. Nothing is ever linked automatically.

Milestone 8 laid the groundwork (nullable `catalog_entry_id` on items, `catalog_entries` with `source`/`status` columns). Migration 0005 added the natural key: entries are unique per category on normalized name + identifier, where `categories.catalog_identifier` names the identifying attribute (set number, ISBN, artist...). Only `status = 'approved'` entries are ever public. Migration 0007 narrowed that key to live entries (pending or approved), so a rejected suggestion never blocks a later one, and added the `moderation_requests` queue (ADR 0012).

## Social — profiles, friends, followers

- **Profiles and privacy** — **shipped** (ADR 0009). Handles, `/u/<handle>` pages, and account-level collection visibility: Public / Followers & friends / Friends only / Private.
- **Friends and followers** — **shipped** (ADR 0014, Proposed). Friend requests (mutual; accept or decline) and follow requests (one-way; every follow needs the owner's approval). Followers are listed for the person they follow, who can remove them; followers are not friends. Accepted friendships and approved follows unlock the matching visibility levels. A People page (Friends, Followers, Following, Requests tabs, plus search among profiles you may see) and a header badge for requests waiting on you. Blocking is not built yet (see the review file).
- **Compare collections** — **shipped.** On a profile (or one of its collections) whose collections you may see, "Compare collections" lines up your items and theirs in one category: both of you, only you, only them, and the category's approved catalog entries neither of you has (with "Add to my collection"). Catalog links match first; free-form items match a catalog entry when their normalized name names exactly one, otherwise by normalized name. See `Documentation/review/collection-compare-review.md`.

## Explicitly Deferred (post-MVP backlog)

- Photo uploads (requires S3 / AWS object storage work).
- Acquired date / price / provenance tracking.
- User-suggested new categories + moderation flow.
- Shareable links to a single collection regardless of account visibility (e.g. an unlisted link). Profiles at `/u/<handle>` already show collections to the people the owner's visibility setting allows (ADR 0009).
- Barcode / UPC scanning for auto-fill.
- Native mobile app build via Capacitor.
- Imports from external catalogs (Brickset, Pop Price Guide, Discogs, etc.).
- Real-time multi-device sync.

## UX Backlog (known-bad surfaces to polish)

_Nothing open right now._

## Known Unknowns (tracked, not blocking)

- Shape of public shareable collections (affects auth model).
- How far we go with curated vs. community-contributed category attribute schemas.
- Postgres full-text search vs. OpenSearch/Meilisearch when the category catalog grows.
- AWS target for Go API: App Runner (simpler) vs. ECS Fargate (more control).

## Seed Categories (initial)

The MVP ships with a curated list:

- Lego Sets
- Funko Pops
- Coins
- Stamps
- Trading Cards
- Plants
- Books
- Vinyl Records

Per-category attribute schemas (with `title` + optional `description` on every property, per the non-engineer-friendly-copy principle) are defined in the reference seed file `api/internal/seed/sql/reference/0001_categories.sql`, embedded into the Go binary via `go:embed`, and upserted into the `categories.attribute_schema` JSONB column on every startup of the API (idempotent). All seed data follows the same pattern: idempotent SQL files in a **reference** set (always applied) and a **dev** set (fake data, applied only with `SEED_DEV_DATA=true` when `APP_ENV` is `development` or `test`). See `Documentation/seed-data.md` and ADR 0007. `Documentation/categories/README.md` documents the schema conventions.
